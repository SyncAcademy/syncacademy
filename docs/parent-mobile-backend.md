# Parent mobile backend

## Current implementation

The Flutter client uses the existing `/api/v1` NestJS API and PostgreSQL database. Parent identity is a `User` with a verified `ParentAccount`; each school keeps its own `Guardian` contact and active `StudentGuardian` links. A contact record or invitation alone grants no student access. Every child read checks the active link, school status, account state, and the link's relevant visibility flag. Staff use the existing school cookie session and selected role.

The mobile client sends `Authorization: Bearer <accessToken>` and no browser cookie. Tokens are random 256-bit values; PostgreSQL stores only SHA-256 hashes in `ParentMobileSession`. A session expires after 30 days, can be rotated at `/parent/auth/renew`, and is rejected after logout, account disablement, or `User.sessionVersion` change. Flutter should store the token in Android Keystore or iOS Keychain backed secure storage, never store the password, and send requests only to the public HTTPS API. The backend refuses insecure parent routes in production. The token is returned only at sign-in or renewal and is never a URL parameter.

Parent API requests from native clients omit `Origin` and `Cookie`; JSON writes use `Content-Type: application/json`. The browser origin restriction remains in force for school staff. Staff writing parent invitations or announcements first fetch `GET /schools/{schoolId}/parent-actions/csrf`, then send its `csrfToken` as `x-csrf-token` with the existing authenticated cookie. The token is held in the PostgreSQL-backed browser session.

### Activation and sign-in

1. A Headmaster, Academic Master, or Registrar creates an individual invitation or a selected-student, class, or school batch. Only active guardian links in the selected school and year are eligible. Each guardian receives a unique 48-hour link and 128-bit manual code through the selected existing delivery channel. The outbox worker checks invitation status immediately before sending.
2. Flutter sends the link token or manual code to `POST /parent/invitations/challenge`. The backend sends a separate six-digit, 15-minute verification code to the invitation's recorded contact. The response includes `codeLength: 6` and a masked destination. Flutter renders one numeric box per digit, supports whole-code paste and native OTP autofill, and retains the separate invitation credential field. Password recovery uses eight numeric boxes for its eight-digit code.
3. Flutter sends the invitation credential, verification code, and chosen password to `POST /parent/invitations/activate`. The transaction consumes the challenge and invitation once, verifies that the contact and relationship are still valid, and links a `User` to the school guardian. For an existing parent account, `password` must match that account. Activation does not return a session.
4. Flutter signs in with verified email or phone and password at `POST /parent/auth/login`. It stores the returned bearer token, calls `/parent/auth/me` and `/parent/children`, and handles `401` by clearing the stored token and returning to sign-in. Child selection is a client preference and never changes server authorization.
5. Logout revokes the current token. Password change, password recovery, and revoke-all invalidate all mobile sessions and existing browser sessions through `sessionVersion`.

An SMS-only parent account uses an internal non-deliverable `User.email` identifier. The public profile returns `email: null`; the parent signs in and recovers by verified phone. If the guardian's email belongs to an account without a parent identity, activation requires school follow-up rather than silently attaching a parent identity to that account.

Flutter configures the public HTTPS origin plus `/api/v1` as its base URL. A successful sign-in response has the shape `{ "accessToken": "<opaque-token>", "tokenType": "Bearer", "expiresIn": 2592000 }`. Subsequent requests send `Authorization: Bearer <opaque-token>`; the app stores the token in platform secure storage and sends no cookie or CSRF header. On a `401`, clear that token and show sign-in. After renewal, replace the stored token atomically. On logout, call `/parent/auth/logout` and clear it even if the network request fails. An HTTP `403` means the signed-in parent lacks permission for the requested child data; a `404` means the child or published item is unavailable in the authorized scope.

The permission boundary is: Headmaster, Academic Master, and Registrar can issue parent invitations; Headmaster and Academic Master can publish approved results and parent announcements; a parent can read a child's data only while an active school guardian link permits the specific resource. The mobile token never grants staff or platform authority.

### Endpoint inventory

### Announcement management and private media (current implementation)

The existing text-only `POST /schools/{schoolId}/parent-announcements` remains compatible. Staff with the Headmaster or Academic Master role may send `{yearId, classId?, title, body, draft:true}` to create an unpublished draft. An omitted `draft` publishes immediately. The authenticated staff cookie, `Origin: <APP_ORIGIN>`, `X-Requested-With: SyncAcademy`, and `x-csrf-token` are required for writes. Staff can `GET /schools/{schoolId}/parent-announcements` (cursor and limit), `GET /schools/{schoolId}/parent-announcements/{id}`, `PATCH /schools/{schoolId}/parent-announcements/{id}` with `{title?,body?}`, `POST /schools/{schoolId}/parent-announcements/{id}/publish`, and `POST /schools/{schoolId}/parent-announcements/{id}/unpublish`. Unpublish is terminal. Each mutation appends an audit event. The worker only fans out notifications for currently published announcements and retains the existing dedupe key.

For an image announcement, upload a single PNG to an unpublished draft with `PUT /schools/{schoolId}/parent-announcements/{id}/media`. Send raw bytes as `Content-Type: image/png` with the same staff headers and CSRF token. Maximum request size is 5 MiB. The raw upload contract transmits no filename; the API validates MIME type, PNG signature, actual decoded format, complete raster, dimensions up to 4096 per side and 12 million pixels, and rejects animated or corrupt images. Sharp re-encodes the original without EXIF metadata and produces display (maximum 1280 pixels) and thumbnail (maximum 480 pixels) PNGs while preserving aspect ratio. Two processing jobs per API instance are allowed; excess requests receive a retryable `429`. There is no JPEG/WebP ingestion, gallery, or media replacement. The upload response includes `{id,mimeType,byteSize,width,height,status:'READY'}`. Publish only after a successful upload; the backend blocks publication while media is incomplete.

The Nginx route for this upload allows 5 MiB requests; the general API request cap remains 32 KiB. Both the proxy and NestJS reject larger uploads before processing.

Parent announcement list and detail responses contain captions and `media: null` for text-only items or public media metadata without storage keys. Parents fetch `GET /parent/announcements/{id}/media?variant=thumbnail|display|original` with their bearer token; the default is `display`. Staff use the equivalent school-scoped route. Every read rechecks the guardian, enrollment audience, publication, expiry and media readiness. Authorized bytes stream from private storage with backpressure, a 5 MiB cap and `private, no-store` headers. Client disconnects cancel storage reads. Old records without generated variants fall back to their original image. Flutter loads thumbnails in the feed, display images in details, and originals only when opening the image viewer. Failed downloads have a retry action. Private images remain in memory, and logout or account session expiry clears the application image cache. Drafts and unpublished items are absent from parent list, detail, and media routes.

`GET /parent/announcements/stream` is a bearer-authenticated SSE invalidation stream. Successful staff mutations publish through the existing `RealtimeBus`; publication sends a metadata-only `changed` event to connected parents in that school. Flutter then reads the authorized feed, so visibility does not wait for the notification worker. Set `REALTIME_TRANSPORT=postgres` on every API replica to carry events across instances using the existing PostgreSQL LISTEN/NOTIFY connection. The stream rechecks account/session and guardian scopes, sends a heartbeat every 15 seconds, rotates after five minutes, limits active connections per parent per API instance, and cleans up on disconnect. Flutter pauses the connection in the background, reconnects with backoff, refreshes on resume, and polls every 30 seconds while live delivery is unavailable. This updates an open foreground app; operating-system background push remains a separate planned integration.

For local development, `ANNOUNCEMENT_MEDIA_PROVIDER=local` writes private files beneath `ANNOUNCEMENT_MEDIA_DIRECTORY`. Docker Compose mounts the named `announcement-media` volume at `/var/lib/syncacademy/media` for the API and worker; the image creates that directory for its non-root runtime user before the volume is initialized. `docker compose down` preserves this volume; `docker compose down -v` destroys it. Back up both the PostgreSQL database and this volume to restore media references and objects together. Files stay outside the web server's public directory. The upload writes to a temporary file and atomically renames it after completion.

For production, set `ANNOUNCEMENT_MEDIA_PROVIDER=s3`, `ANNOUNCEMENT_MEDIA_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com` (or the provider's compatible HTTPS endpoint), `ANNOUNCEMENT_MEDIA_BUCKET`, `ANNOUNCEMENT_MEDIA_ACCESS_KEY`, and `ANNOUNCEMENT_MEDIA_SECRET_KEY` in the API and worker secret environment. Set `ANNOUNCEMENT_MEDIA_REGION=auto` for R2 or the actual AWS S3 region. Create a private bucket and grant only object read, write, and delete permissions in that bucket; disable anonymous access and public listing. Configure identical storage values on every replica. The maintained AWS SDK v3 signs requests and retries transient provider failures with bounded connection/request timeouts. Clients receive neither credentials nor object keys. Production refuses the local provider. A real bucket and credentials must be configured and smoke-tested before launch; repository tests use isolated compatible storage rather than a live R2 account.

Before writing objects, the API inserts a tenant-scoped `PENDING` record containing the server-generated keys and storage provider. It marks the record `READY` only after all three objects exist. Failed uploads become `FAILED`; a worker claims expired `PENDING`, `FAILED`, or `CLEANING` records and idempotently deletes their objects, temporary local files and metadata. Interrupted uploads become eligible after one hour; failed uploads are eligible immediately. Cleanup leases prevent simultaneous workers deleting the same upload, and `READY` media is never eligible. A lost transaction acknowledgement is checked before deleting any objects. Unpublishing retains completed media for staff review while immediately blocking new parent reads. Already downloaded pixels cannot be recalled from a device. No public or temporary bearer image URL is issued.

Deploy the additive `202610240002_announcement_media_lifecycle` migration with `npm run migrate --workspace=apps/api` before the API and worker. It preserves existing objects and marks historical media as `READY` with provider `s3`. New records remember their provider, so changing the default never silently redirects old reads. When moving local development media to object storage: stop uploads, back up PostgreSQL and the media volume, copy each referenced original/display/thumbnail key to the private target bucket, verify byte counts and SHA-256 hashes by reading back the copies, then transactionally update only those verified records' `storageProvider` to `s3`. Test authorized reads before removing the old copies. Restore database metadata and object backups together. Never bulk-delete objects based only on bucket age; retained published and draft announcements may still reference them.

Image-processing logs record duration and byte counts; storage and cleanup failures log safe event types without credentials, signed URLs or image content. Capacity depends on measured image sizes, processing CPU, active SSE connections and provider throughput. No concurrency claim beyond the executed tests is implied.

All paths below start with `/api/v1`. JSON bodies reject unknown fields. UUID path parameters and cursor/limit inputs are validated. `400` means invalid input or challenge, `401` means sign-in or account verification failed, `403` means the role or visibility flag forbids access, `404` means a scoped record is unavailable, `409` means a duplicate or stale state, and `429` means the PostgreSQL-backed rate limit was reached. Invitation validation uses a consistent public error and does not return student details.

### Database and performance review

The new migration adds `ParentAccount`, `ParentInvitation`, `ParentInvitationBatch`, `ParentMobileSession`, `ParentRecoveryChallenge`, `ParentAnnouncement`, and `ParentNotification`. Unique token and code hashes prevent credential reuse; guardian/student relationship constraints remain intact. New compound indexes serve school-scoped invitation lookup, batch leasing, user notification paging, mobile session revocation, and school announcement paging. Existing `StudentGuardian` indexes on `(schoolId, studentId)` and `(schoolId, guardianId)`, enrollment indexes, and fee indexes support the shared authorization checks. Historical migrations remain unchanged.

The parent result endpoint selects one approved report element inside PostgreSQL rather than transferring the whole academic-year workspace JSON. Attendance similarly projects one student's entries in SQL. Fee totals use database aggregates, while charge, payment, and adjustment rows have separate bounded cursors. The existing report publication path now preloads eligible students, guardian links, and enrollments in two queries instead of repeating those reads for every report. The remaining per-recipient writes create distinct links, outbox rows, and audit trails. The JSONB report and attendance scans remain a likely cost at large schools; materialized student-scoped records should be considered after measured query plans justify them.

There is no cross-parent or cross-school data cache. Sensitive reads are served from PostgreSQL with `Cache-Control: no-store`, so relationship revocation and publication changes take effect on the next request. A future shared cache would need a key containing school ID, user ID, student ID, resource ID, and publication version, short TTLs, and invalidation on changes. An in-process cache is inappropriate across API replicas.

The worker leases outbox rows and parent batch/announcement work through PostgreSQL `FOR UPDATE SKIP LOCKED`. It resumes batch work from an indexed guardian cursor, issues distinct invitation credentials, and skips existing active invitations. Announcement notifications use a cursor and unique dedupe key. A worker crash may cause a delivery retry after a lease expires; external SMS/email providers should support an idempotency key for strict exactly-once delivery. Pending invitations and recovery codes are checked again before dispatch. Large school batches still need operational monitoring for provider limits and queue depth.

Existing API process metrics record route latency, error rate, process resources, and session-pool state; the worker publishes heartbeats and queue observations. Query counts and individual query timings are not currently instrumented, so those measurements and PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` on representative parent data remain deployment checks. Configure Prisma connection limits in the database URL and budget `API replicas x Prisma pool + session pools + workers` below the managed database connection cap. Browser sessions and mobile credentials are in PostgreSQL, and leases work across replicas; use a load balancer with HTTPS and `REALTIME_TRANSPORT=postgres` only if staff realtime events span replicas. The open announcements feed uses an authenticated, reconnecting SSE stream with PostgreSQL-backed events across replicas. Durable in-app notifications are worker-generated; background push is not implemented.

### Deployment and verification limits

Apply the additive migration before starting the updated API and worker. Keep the existing Docker Compose services and configure the current email/SMS providers for real delivery; no push provider is present, so push delivery is a future integration. The activation link points to the configured app origin and needs a Flutter deep-link or web handoff when the mobile client is built. The manual code remains available without that handoff.

The shared system currently has no general lesson timetable or event calendar records; the timetable endpoint returns an explicit unavailable state and the calendar returns configured academic terms with an empty events list. The existing public report route named `/pdf` returns JSON rather than a PDF file. Parent mobile results therefore expose the authorized report data and do not claim a downloadable PDF. A real document renderer and authenticated binary download route remain integration work if PDF export is required.

### Parent acceptance test

1. As Registrar, Headmaster or Academic Master, select a student with an active guardian relationship and send a parent invitation through a configured email/SMS channel.
2. In a fresh app installation, complete or skip onboarding. Paste the invitation link or manual credential, request verification, and enter or paste the six-digit verification code. Create a password of at least 12 characters; an existing parent uses the current account password when linking another school.
3. Sign in with the verified phone number or email. Switch between linked children and schools, then check the permitted results, fee information, attendance and calendar. Unpublished results and unlinked children must remain unavailable. Timetable data and online payments are not implemented.
4. Keep the announcements feed open. Publish a PNG post with a caption from the Headmaster or Academic Master dashboard. Check automatic arrival, thumbnail, detail image and full image. Restart the API and check that the image still loads. Unpublish the post and confirm it disappears.
5. Read a notification, edit the profile name, change the password, sign out and sign in again. Test recovery using the eight-digit code. Revoking the guardian link must remove that child's access; disabling the parent account must prevent login.

Automated parent integration tests use disposable PostgreSQL databases and mock communication dispatch. Real email/SMS delivery, a real private production bucket and operating-system background push are separate deployment checks. Background push is not implemented; foreground announcement updates are implemented.

No capacity claim follows from unit tests or a TypeScript build. Load tests should use a disposable PostgreSQL database, representative schools, real guardian links and academic workspaces, mock communication dispatch, and 100, 500, then 1,000 clients with realistic think times. Record hardware, dataset sizes, throughput, p50/p95/p99, error rate, payload sizes, query plans, pool utilization, queue depth, CPU and memory. A provisional budget is p95 below 500 ms for lightweight child reads under the documented workload; results and large-year JSON scans need their own measured budget. Scale API replicas and worker concurrency only after these measurements, keeping a single logical backend and database.
