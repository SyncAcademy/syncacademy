# Academic storage migration and scale gates

This design applies to every school and every database with this application schema. It is a migration plan, not an applied schema change or a capacity guarantee.

## Current bottleneck

`AcademicWorkspace` stores marks, attendance history, reports, support, audit and settings in one year-level JSONB row. Serializable retries prevent lost updates but unrelated commands still contend on that row. SQL projections reduce transfer and Node memory; they do not remove PostgreSQL TOAST rewrites or the shared row lock. Increasing transaction timeouts or the connection pool can make the queue worse.

The 16 October continuation adds a bounded marks command path within this same storage model: it reads the selected submission, executes the existing validation, and merges that submission plus its audit entry inside PostgreSQL. It retains document/submission revision checks, serialization retries, unknown root fields and roster archives. This follows the existing support-save approach and is not a storage migration. Large-document probes now succeed for this path, while attendance and report commands still fail under the measured concurrent workload. The migration gates below therefore remain necessary; the optimization does not establish row-level independence or production capacity.

## Incremental cutover

1. Start with marks submissions and attendance registers, measured separately under load. Introduce `AcademicSubmission` keyed by `(schoolId, yearId, id)` with class/subject/assessment references, revision, status, roster and frozen grading policy. Initially keep one bounded class/subject/assessment payload per row so the existing command contract and aggregate conflict semantics remain unchanged. Separate immutable submission archives from the current row. A later per-student marks table must explicitly preserve submission-level review/submit atomicity.
2. Introduce `AttendanceRegister` keyed by `(schoolId, yearId, classId, date)` with revision and current entries; keep immutable `AttendanceRevision` rows keyed by register and revision. An absent register has revision zero. A conditional insert/update plus history insert must commit together. Two initial inserts race on the unique key and one returns 409.
3. Use composite tenant foreign keys: school/year, school/class/year, school/subject and school/student. UUID uniqueness alone is not tenant isolation. Apply the same selected-role, active membership, class-teacher and subject allocation checks on every read and write. Preserve all historical rosters and grading snapshots even when students move or teachers change.
4. Add a per-year migration marker (`legacy`, `copying`, `relational`) and schema version. Backfill one bounded year/class batch at a time. Record source revision, counts and content hashes, validate references, and quarantine malformed history. Reruns must be idempotent. Do not delete or repair original JSON implicitly.
5. While the marker is legacy, existing commands remain the only writer. Copying is a shadow read-validation phase, not dual ownership. At cutover take a short year advisory lock that **all academic and registry writers must acquire**, verify the source revision still matches, copy the remaining delta, compare authorized API output and flip the marker transactionally. Include subject renaming, teacher reassignment, class deletion, allocation, year closure, report generation and registry defaults in the writer inventory. Any unknown writer blocks cutover. Drain old API binaries before enabling relational mode.
6. In relational mode use `UPDATE ... WHERE revision = :loadedRevision RETURNING revision`; zero rows means 409. Allocate/save/submit/review use the same revision contract. Never read a fresh revision to authorize a stale draft. Mutation receipts expose the committed record revision, not whichever version a later GET sees. Keep bounded retries only for database serialization failures; never retry semantic 409s automatically.
7. Keep the original REST endpoints as adapters over the selected storage mode. Prefer summary queries, bounded lists with server filters, and selected-submission detail reads. Legacy full-year APIs remain compatibility paths until all consumers and exports are audited. Multi-row reports read a consistent snapshot and record the source submission revisions; publish immutable generated report versions. Large report jobs should be queued and streamed/downloaded rather than tying up an HTTP transaction.
8. Avoid reintroducing contention through an updated year counter on every save. Use a sequence-backed change/outbox table containing school, year, entity, entity version and event ID. Write it in the business transaction. A sequence gap is harmless. Reconnect can query changes after a cursor or fall back to a full authorized scoped refresh. Bound retention and explicitly signal expired cursors. The current invalidation transport is a hint and is not this durable outbox.
9. Test tenant/role isolation, stale drafts, duplicate requests, concurrent first writes, review racing marks, corrections/history, allocation replacement, migrations restarted halfway and a mixed-history year. Compare old/new authorized projections and report hashes. Shadow production reads before enabling one pilot year, then expand by configuration without hard-coded school identifiers.

## Deployment and rollback

Run additive migrations as the migration owner on every database, then rerun `provision-runtime` for new tables. Runtime retains no schema-creation privileges and cannot update/delete audit rows. Run backfill using a separately authorized migration identity. Rebuild and deploy API and frontend together; preserve the WebSocket reverse proxy. Backups must have a tested restore procedure before cutover.

Rollback before cutover only disables the new reader. After relational writes begin, do not flip back to stale JSON. Either keep the relational compatibility reader or perform a verified reverse export under the same writer lock. Retain source JSON through the agreed audit/backup retention period.

## Measurement gates

Use a disposable database and at least 12 schools, each larger than the previous 1,800-student fixture. Exercise distinct-school writes, same-school distinct submissions, same-submission conflicts, attendance corrections, dashboard refreshes and reports together. Record p50/p95/p99/max per operation, throughput, expected 409s separately from failures, process RSS/heap, database active/total connections, transaction retries, lock waits and query plans. Include network/browser measurements on deployment hardware before capacity sign-off. Add indexes or caches only when those measurements identify the query and improvement; measure write cost and cache invalidation too.
